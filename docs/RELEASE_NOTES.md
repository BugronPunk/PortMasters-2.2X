# PortMasters 2.2 Parallel Release

This is the release note for the 2.2 build. It answers one question: the game already exists in an earlier build, so what is different now?

The short answer is that PortMasters 2.2 Parallel Release is a build of its own rather than a patched copy of the one before it. Every rule, every price and every system that build established is still here, working the same way, and six whole systems are built on top of them. The interface, the realtime layer and the way the process starts up were rebuilt around that.

## The build before this one

The earlier build is [PortMasters 2 Parallel Release](https://github.com/LostInHustle/PortMasters2-Parallel-Release), written by Joe Zhou and Aaron Zhu. That is where the multiplayer game as it exists today was designed. The deterministic engine, the ready check, the three difficulty tiers, the social economy and the Ledger Integrity Pass all come from there.

The 2.2 build branches from it rather than patching it. Every game system that build shipped is still in this one. Only two files were dropped along the way. One is the single file realtime layer, which was split into modules. The other is a Hello World stub on `/api` that answered nothing and that nothing called.

The tree figures in that table are measured rather than rounded, and the rule is worth writing down because no check reads the docs: the realtime layer counts the `.ts` files under `src/server/realtime` with the `conclusion` subdirectory left out, the engine counts the `.ts` files under `src/lib/game/engine`, and the interface counts the `.tsx` files under `src/components`. Measure them again the same way after any pass that adds or removes a file.

## The six systems 2.2 adds

Each of these is a numbered entry in the Harbor Manifest, the design document that listed eighteen systems and shipped ten of them. These are six of the seven that were still on that list when 2.2 started.

### Partial Sight (Manifest 06)

Renown buys a clearer view of the captains you sail with. A captain at Renown level 5 or above, which the game calls a Trade Officer, sees the detail of any captain at level 3 or above: what is in their hold and roughly how much Gold they carry. Below either threshold, the viewer sees only the headline numbers, the level and the title.

The hold is shown as a band rather than a count, so a partner can tell a few from a haul without reading your ledger. The bands are none, a few up to three, some up to eight, plenty up to fifteen, and a haul beyond that. This adds no new trust boundary. The numbers were already being sent to every client in the harbor, and the banding happens on the client that is looking.

### Great Houses (Manifest 08)

A captain may pledge to one House. The pledge is account level, so it carries across every voyage, and it can be changed at any time between voyages. The three Houses map onto the three corners of the voyage loop.

| House          | Motto                            | What it stands for         |
| -------------- | -------------------------------- | -------------------------- |
| Jade Pavilion  | Patience polishes the stone.     | The artisan economy        |
| Vermilion Gate | The gate is open to every cargo. | The market and cargo trade |
| Golden Lotus   | Fortune favors the bold wager.   | The wager economy          |

A pledge is a second identity alongside Renown, and it is deliberately kept separate from it. Renown measures how long you have sailed. A House says what kind of captain you are while you do it. Every pledge also feeds a harbor wide House standing, so the three Houses compete on total crowns, voyages and best Reputation rather than on any one captain's numbers.

Each House carries one small passive perk, applied at the start of every fresh voyage and never partway through one. Jade Pavilion's first artisan joins at no cost, with the first wage on the House. Vermilion Gate adds one more cargo lot to the Port Purchase board, every round. Golden Lotus pays 20 percent less in wages against a raid chance 5 percent higher. None of the three touches a number that compounds, which is what keeps a pledge a flavour rather than a power pick. A captain can change House between voyages, and the new perk takes effect on the next start.

### Ages of the Ledger (Manifest 10)

The three peer economy tools take turns in the spotlight. Each Age holds for two weeks, then the next takes over, and after the third the cycle starts again.

| Age               | What it is designed to reward                              |
| ----------------- | ---------------------------------------------------------- |
| Age of the Lender | Backing another captain's loan pays 50 percent more Renown |
| Age of the Trader | Every completed barter trade lands one extra Reputation    |
| Age of the Broker | The Broker's Favor commission cap rises to 250 Gold        |

Every captain in every harbor is under the same Age at the same moment, so an Age changes what the harbor rewards, never who is in it. The cycle is anchored on the Unix epoch rather than on any server's clock, which means two captains in different time zones work out the same Age from the same timestamp.

The rotation is live, the banner that announces it is live, and each of the three rewards is applied where it lands. A backing pledge pays its extra Renown when the pledge resolves. A completed barter trade lands its extra Reputation on both captains, so it is the trade that earns it rather than whichever captain happened to post the offer. The Broker's Favor commission cap is read from the Age in force, so every quote and the payout itself move together. Each effect stays deliberately small, a lean rather than a dial, so an Age cannot unbalance a voyage that began under a different one.

### Captain's Rival (Manifest 11)

The captain you keep sailing against gets a scoreboard of their own. Every time two captains finish a voyage in the same harbor, the meeting is recorded with its outcome, and the pair accumulates wins, losses and ties across every voyage they have sailed together.

The pair is identified by a key built from the two account ids in sorted order, so a meeting recorded as Lin against Wei is the same record as Wei against Lin. One record serves both captains and neither needs a second copy. The head to head line sits on the Legacy card and appears only when both captains are in the same room, so it reads as a rivalry rather than as a statistic.

### Voyage Chronicle (Manifest 12)

A finished voyage already showed a hard ledger of rounds, peak Reputation, final Gold and taxes. The Chronicle is the prose layer on top of it: a one sentence headline and a body of three to five sentences, written at the moment the voyage concludes and stored so a captain can read it again later.

The headline names the captain and the waters they actually sailed, and leads with the crown if they took it or with the loss if they went bankrupt. The body carries the rounds, the peak Reputation, the largest single trade, how much lending and borrowing happened, and the closing line. It is a pure function of the numbers, so the same voyage always produces the same prose, and it never dresses an outcome up. A bankrupt voyage gets a Chronicle too, one that says so plainly.

### Quick Start Match (Manifest 17)

A captain who just wants to play, without rounding up a room code or waiting for a friend, presses Quick Start. The queue seats them in the first open public harbor with a free seat, or opens a fresh one and makes them the host. The tier they picked in the Lobby before pressing the button is the tier a fresh harbor opens at.

Two captains pressing the button in the same tick used to be seated in two different harbors, because both looked for an open room before either had created one. Matches are chained now, so the second waits for the first to finish, and the room the first captain opened exists by the time the second one looks for it. A harbor whose remaining members have all closed their tabs is skipped as well, since it is not open, it has simply not been cleaned up yet.

## A rebuilt interface

The most visible change is how the game looks and how much of it explains itself while you play.

The palette is drawn from East Asian art and the morning sea. Celadon green as the primary, the colour of the porcelain that gave the trade its name. Vermilion as the accent, the colour of the seal stamped on every manifest. Imperial gold for warmth, indigo for depth, and rice paper cream as the canvas. Panels are glass floating over a sea gradient, and the textures behind them are seigaiha waves and crackle glaze. Display headings are set in Noto Serif SC, which carries a little brushwork without costing legibility.

Eleven screens and panels are new.

|                    | What it does                                                               |
| ------------------ | -------------------------------------------------------------------------- |
| How to Play        | A nine step walk through a voyage, readable from the Lobby before you sail |
| Settings           | Sound, colour preference and the rest of the per captain options           |
| Keyboard shortcuts | The full key map on one screen                                             |
| Captain profile    | Another captain's public record, opened from the roster                    |
| Difficulty advisor | Suggests a tier based on how much time a captain has                       |
| Action suggester   | Names the next worthwhile move instead of leaving a new captain staring    |
| Voyage timeline    | Where the voyage has been and where it is going                            |
| House leaderboard  | The three Houses ranked by crowns, voyages and best Reputation             |
| Leaderboard        | Captains ranked across the whole game                                      |
| Sparkline          | A small trend line, used wherever a number moves over time                 |
| The Age banner     | Which Age holds the harbor, and what it is rewarding right now             |

Sound is new as well. The tones are synthesized at runtime through the Web Audio API rather than loaded from files, so there is nothing to download and no asset to lose. A wooden clapper marks a confirmation, a soft bell marks an arrival and a low drum marks a warning, over a quiet ambient bed that only plays while the page is visible. The toggle and the volume both persist on the device.

The room is laid out to the screen it is standing on rather than to the window behind it. On a wide screen it is an app shell, with three columns that each scroll inside themselves and the controls pinned under the board, and every board inside the middle column is measured against that column instead of against the window, so a market that has room for two cards deals two rather than three narrower ones. The two rails are held to about a fifth of the window each rather than a quarter, which leaves the board itself roughly a hundred and fifty pixels wider than it was, and the captain's own identity is a line on the left rail instead of a card on the table's board. On a phone the page is one document that never scrolls sideways, and the keyboard shortcuts live on the control bar, drawn only where there is a keyboard to press. `docs/SYSTEM_ANALYSIS.md` carries the rules and the measurements under "The Room's Width".

The two operator screens are laid out the same way, to their own column rather than to the window. The console draws the roster as a table where the column has room for one and as a card per account where it does not, and it decides between the two on the column's own width: as a table the register needed 1,034 pixels in a column capped at 976, so at every desktop size an operator had to drag the roster sideways to reach the buttons, and on a phone the drag was 485 pixels, which means an operator acting on an account could not see the name of the account they were acting on. The row buttons gave up their conditional labels in the same pass. They had been words on a wide window and bare icons on a narrow one, decided at 1,280 pixels of window while the column they were drawn in was 1,024 whatever the window did, so on a 1,024 desktop five unlabelled icons sat with room to spare and past 1,280 the words arrived and pushed the table 60 pixels wider than the column holding it. Every button on the screen says what it does now. The balance dashboard reads its own column too, so its four front page tiles no longer jump from two across to four across at a window size where the column has not moved, and the panels below carry their readings as a table where there is room and as a row per reading where there is not, which took the 308 pixel drag off a phone. `docs/SYSTEM_ANALYSIS.md` carries the measurements under "The Operator Screens' Width".

A cleanup pass followed the two redesigns and took the repetition out of the game's own markup. The close button on the five dialogs is one component now, having been five identical copies down to the icon's size. The row an offer is drawn as on the escort market, the refit bench and the barter board is one component too, along with the chip that marks an offer aimed at one captain, so a captain's own offer is tinted the same way on all three desks. And the four dropdowns on the manifest audit, the bazaar's desk and the maroon vote now use the shared `Select` the other four boards already used. Three repeats were looked at and left alone, with the reasons recorded under "The Shared Surfaces" in `docs/SYSTEM_ANALYSIS.md`, and nothing about how the game plays changed.

The two operator screens were laid out again in the cycles that followed, first to be fluid between a floor and a cap rather than held at one width, and then to give the caps up altogether. The console's column once read `clamp(56rem, 96vw, 80rem)` and the balance page's `clamp(56rem, 96vw, 76rem)` where both were capped flat at 1,152 and 1,024, which is what had the register drawing 1,104 pixels of content inside a 2,560 pixel window while the dashboard drew 976; at their caps the two stood at 1,232 and 1,168, and today both screens run the window's full width behind a clamped gutter, `px-[clamp(0.75rem,2.5vw,3rem)]`, so every pixel past the gutter belongs to the register. The register reads six columns rather than seven, the role having folded into the identity cell as the chip beside the display name, and its table and card presentations divide at 52rem of column rather than 60, the threshold measured again rather than assumed: the six column table measured 881 where it needed 958 before the fold, drawing the row actions as quiet words took the floor down to 817, and with the frame's two pixels of border the table stands at 819 where 52rem is 832. The width probe caught the first guess of 54rem drawing the table at a 960 pixel window with a nine pixel drag to the Actions column. The roster gained a search field over names and handles and four counted filters, the counts taken off the set the search matched so a chip never promises a count its press cannot keep, and selection follows the view: the header checkbox acts on exactly the accounts shown, stands indeterminate on a partial tick, and a tick survives a filter change, so an operator can tick across views and act once. On the wide layout the console is an app shell one window tall with the register as its only scroller and its header cells pinned to the frame's top, and on a narrow one it is still a document that scrolls the way documents do. The balance page's subtitle stands up to two lines instead of truncating, its largest numbers went one type step up with their pills held against squeezing, and its reading tables took the register's row padding. Nothing about how the game plays changed.

## A rebuilt realtime layer

The realtime layer was one 3,097 line function. It is now thirty five small modules under `src/server/realtime`, each owning one concern: presence, the checkpoint protocol, barter, aid, loans, ventures, chat, conclusion, pulse, objective, docks, surge, rival, quickstart, status, admin, auth, gambit, audit, maroon, reveal, save, telemetry, the bazaar, the refits, the escort contracts, the consent record, the module market, the path draft, the voyage log, the boon ledger, the row id minter, the inbound frame limit, the shared types and the composition root that wires them together. The `socket.on` registrations that root used to declare now number seventy two, seventy of them one concern to a file under `src/server/realtime/wiring`, twenty seven leaves that nothing but the composition root imports, and two beside the leaves, each named in the order a connection takes its shape rather than carried in the root's own body.

The telemetry module is the newest of them and the only one that is silent during play. It holds a voyage's measurement in memory while the voyage runs and writes it as a single row when the voyage stops, so the harbor never waits on the database to be recorded, and it samples per voyage rather than per event so the share of voyages recorded is one setting. Nothing reads a record back during play, and no rule of the game changes because a voyage was recorded.

Each record closes with a line per captain, and two of the fields on that line are worth naming because they are the two numbers the design would rather not reconstruct later. One is whether the harbor's carried vote put that captain ashore, written at the moment the vote carries rather than derived from the events, so a voyage that ends by a wipe or by the harbor emptying still carries the mark. The other is what that captain's own save says they took from other captains in trade, read through the same reader the Broker's verdict uses, so the number on the line and the number the rule decided on cannot be two readings of one save. The conclusion reads the room's saves once, at the moment the voyage ends, and hands that one parse to the record, to the integrity verdict and to the chronicle, which is two reads fewer than it used to make of the same rows.

Two shapes moved somewhere both halves can reach. `PublicUser` and `CaptainStatus` now live in `src/types/realtime/` with no runtime dependencies, so the client and the server are described by one definition rather than two that drift apart. The synchronized phase order moved to `src/lib/game/checkpoint.ts`, so the ready check and the interface read the same list from the same place. [B1] moved it one place further in, onto the mode record as `checkpointPhaseOrder`, because the two modes walk the same six phases in different orders and an order belongs to a voyage rather than to the protocol that reads it.

The reason to care is not tidiness. Code buried inside a socket closure can only be reached by starting a server and driving it over a socket. Code in a module can be imported and checked on its own, which is something the rules engine has always been able to do and the realtime layer could not.

## Configuration and boot

The previous build read `PORT` where it happened to be needed and otherwise assumed a working environment. 2.2 reads the environment once, at boot, and validates it.

| Variable           | Value in `.env.example` | What it does                                                  |
| ------------------ | ----------------------- | ------------------------------------------------------------- |
| `DATABASE_URL`     | `file:../db/custom.db`  | The SQLite file holding every account, harbor and voyage      |
| `PORT`             | `8080`                  | The port the whole game answers on                            |
| `HOST`             | `0.0.0.0`               | The bind address, so another device on the network can play   |
| `ADMIN_SETUP_CODE` | a placeholder           | The one code that admits an operator account through `/admin` |

A port that is not a whole number between 1 and 65535, a missing database URL or a database URL that names neither SQLite nor Postgres stops the server with a message naming the variable it did not like. Every problem is reported at once rather than one restart per mistake. Binding `0.0.0.0` by default is what lets a phone on the same wifi open the game, and what lets one tunnel put the whole thing online.

`DATABASE_URL` is the one entry with no fallback, and the operator code fails closed rather than open, so a fresh checkout copies `.env.example` to `.env` before its first run. `next.config.ts` reads two more while the development server is up, `ALLOWED_DEV_ORIGINS` and the host's own `RAILWAY_PUBLIC_DOMAIN`, which together decide which hostnames may load development resources. The README covers both of those as well as `ENV_FILE` and `SMOKE_BASE_URL`.

`NEXT_PUBLIC_SURVIVAL` is not read the way the table above reads, and it is worth the paragraph rather than a row. It gates the provisions layer, and the rules it gates run in the browser, where the engine runs, so it carries the `NEXT_PUBLIC_` prefix and the browser's copy of the value is fixed when the bundle is built: turning the layer off takes a rebuild and a restart rather than a restart alone, and the server reads the same value from the same file at run time when it assembles an audit reveal. Unset is the layer on, which is the state this branch ships in, and the word `off` or the digit `0` turns it off. Nothing about a voyage is stored differently either way, because the Larder is a field every save carries whether or not a rule reads it.

`NEXT_PUBLIC_CREW_LOSS` is the second switch of that pair, and it reads the same way through the same policy function, so the two cannot drift in what they accept. It gates the permanence alone rather than the roster: with it off a captain still meets named artisans and loses none, and a run of hungry legs in progress resets rather than waiting to spring the moment an operator turns it back on. The layer above governs it, since without a shortage there is no loss to follow, so a build with `NEXT_PUBLIC_SURVIVAL` off loses nobody whatever the loss flag says. The rebuild note above applies to it for the same reason, because its rules run in the browser too.

`NEXT_PUBLIC_GARMENTS` is the third switch of that family, read through the same policy function as the two above so that no flag of the three can accept a value another refuses. It gates the cold alone rather than the clothes: with it off nothing is read of the wardrobe, nothing wears out and nobody freezes, while the clothes a voyage is already carrying stay on it exactly as they were read. The layer above governs it as it governs the loss rule, so a build with `NEXT_PUBLIC_SURVIVAL` off has no cold whatever this flag says. The rebuild note above applies to it for the same reason, because its rules run in the browser too.

`NEXT_PUBLIC_SPLIT_HOLD` is the fourth switch of that family, read through the same policy function as the three above so that no flag of the four can accept a value another refuses. It gates the hold's shape and nothing else: with it off there is one unbounded pool for goods, the market refuses nothing for room, food falls back under the Larder's own sixty meal ceiling, and the panel's two capacity lines are not drawn, so the header reads the way it read before the split. The three foods, their keepings and the preserve above them are deliberately not this switch's to turn off, because they belong to the provisions layer: the plan ships the foods and the hold in one slice and puts the riskier half, the capacity model, behind its own flag, so a table that rolls the hold back still meets the pantry. The layer above governs it as it governs the rest of the family, so a build with `NEXT_PUBLIC_SURVIVAL` off plays the base game whatever the split flag says. The rebuild note above applies to it for the same reason, because its rules run in the browser too.

`NEXT_PUBLIC_PATH_ORDERS` is not one of that family and no layer sits above it, which is worth a sentence because it is the first switch in this tree that stands alone. It gates the three pathbound cards on the trade board, and it is read at both ends of a card's life: with it off the draw appends no slots and the lock rule answers that no card is anyone's locked order, so a board dealt while it was on plays as six ordinary orders rather than as a table where three cards stay grey forever. The rebuild note above applies to it for the same reason as the rest, because the rule runs in the browser.

`NEXT_PUBLIC_ESCORT_CONTRACTS` is the sixth switch and the second that stands outside the provisions family. It gates the escort contract, and the plan's rollback clause is why: a contract is transient room state rather than durable. With it off no contract can be posted, because the server refuses one, no board is drawn and the raid roll reads no cover, so a voyage plays exactly the raid it played before the feature existed. A contract already agreed when the switch goes off loses its cover rather than being cancelled, which is the same shape as a rolled back path order losing its lock. Nothing about a voyage is stored differently either way, because a save carries no contract at all. The rebuild note above applies to it for the same reason as the rest.

`NEXT_PUBLIC_REFITS` is the seventh switch, and it is the one that stands on another switch rather than beside one or outside them all. It gates the Loom's refit bench, and it is judged beside the bench rather than in the shared flags module, because a refit is a rule about garments and there is nothing to put right on a table with no clothes layer: `refitsOn` asks the wardrobe layer first and answers false whatever this flag says, so a build with `NEXT_PUBLIC_GARMENTS` off has no bench, no pile and no reweave. With it off no refit can be offered, because the server refuses one, no board is drawn, and none of the bench's three actions happens: no tailor puts a point back, no rag comes off the pile, nothing is rewoven. A refit already agreed when the switch goes off stands for the leg it was agreed for and puts no points back, which is the shape the contract above takes. Nothing about a voyage is stored differently either way, because a save carries no refit at all, and the four numbers the bench keeps are zeros rather than readings the other build would miss. The rebuild note above applies to it for the same reason as the rest, because the rule runs in the browser.

`NEXT_PUBLIC_BAZAAR` is the eighth switch and the third that stands outside the provisions family. It gates the bazaar rumor, and it is read at both ends of the draw rather than in the middle: with it off the server sends no lean at all when a harbor moves to the next leg, and the market folds none in when it prices a card, so a rule that could not otherwise answer anything but an empty object is not given a second place to be written. With it off no rumor can be published, because the server refuses one, no desk is drawn and no price moves, so a voyage plays exactly the voyage it played before the feature existed. A rumor already standing when the switch goes off stops moving a price rather than being withdrawn, which is the shape the two switches above take. Nothing about a voyage is stored differently either way, and that sentence carries one clause the others do not need: the lean a market was priced against is a field every save carries whether or not a rule reads it, the way the Larder is, so a voyage saved in either build reads back in the other and a save written before this feature reads as a market nobody leaned. The rebuild note above applies to it for the same reason as the rest, because the rule runs in the browser.

`NEXT_PUBLIC_PATH_DRAFT` is the ninth switch and the fourth that stands outside the provisions family. It gates the path draft and the one change of papers a voyage allows, and it is read at both ends of both and at the lap fold that seats the deal: with it off the lap carries no draft seat at all, the server deals no cards when a voyage leaves the dock, no hand is sent to any seat, no switch can be published because the room refuses one, and the identity panel draws nothing at all, so a table plays the pathless voyage this tree sailed before the feature existed, and every pathbound card is locked, which is a refusal the lock already answers without a rule of its own. The rebuild note above applies to it for the same reason as the rest, because the rules it gates run in the browser: the panel reads the flag at render time, and the two writes an engine makes are not behind it, because they judge the save they are handed rather than the build they are running in. What it does not do is empty a save: the path a captain holds is a field their own save carries, and a build with the deal switched off leaves it standing rather than taking it back, which is the shape the escort contract and the rumor take. Nothing about a voyage is stored differently either way, and that sentence is the plainest of the four: the draft is not stored at all, since the deck, the hands and the absence watch are the room's memory of one voyage and are dropped with it, and the two fields a path leaves behind are the ones every save in this tree carries whether or not a rule reads them.

`NEXT_PUBLIC_MODULE_TRADES` is the tenth switch and the fifth that stands outside the provisions family. It gates the module market, the Parley table where one captain sells a module bolted to their hull to another, and the plan's rollback clause is the reason its read sits where it does: modules are durable, so the rollback is data rather than code, keep the table and stop the equipping rather than dropping anything a voyage is carrying. With it off no module can be listed, because the server refuses one, no board is drawn, and a row already agreed settles nothing on either side: the seller keeps their module, the buyer keeps their Gold, and a module that would have left a hull stays bolted to it. That sentence is kept true by where the flag is read, at the top of the settle itself rather than at the panel alone, so a board a table agreed to a moment before an operator turned the switch off costs nobody anything, which is the shape the escort contract above rolls back in. It stands on no other layer, which is the escort's reading rather than the refit's: a module is base game, the hull that carries one has existed since the first shipyard, and nothing has to be true of another system before this one can answer. Nothing about a voyage is stored differently either way, and that sentence is the plainest here, because what a captain has bolted on lives in their save beside their hold and their purse, nothing this feature added writes to it, and a save written in either build reads back in the other. The rebuild note above applies to it for the same reason as the rest, because the panel reads the flag at render time and the rules it gates run in the browser.

`NEXT_PUBLIC_MILESTONE_BOONS` is the eleventh switch and the sixth that stands outside the provisions family. It gates the five milestone moments: a hand lost overboard, a first pathbound order, a rung of renown crossed, a cold leg sailed, and a commission carried home, each of which deals its own draft of boons at the moment it lands rather than at the round's turn. The plan's rollback clause is the reason its read sits where it sits: boons are additive and rare, so the revert stops the dealing rather than revoking what was dealt. With it off no moment is ever armed, because the arming path asks the switch first, and no draft is drawn even over a save that carries a moment waiting, because the drawing rule asks it too, so a table plays the voyage this tree sailed before the feature existed. What it deliberately does not do is take a boon back: a card already in a captain's hands keeps its flag for the voyage, and the rail that lists those cards is not read through the switch at all, because a row hidden behind it would be a screen lying about effects the captain still holds. It stands on no other layer: the five moments read the crew, the order board, the renown ladder, the cold and the commission, all of which exist without it. Nothing about a voyage is stored differently either way, because the held cards, the waiting queue, the marks and the names of the crew lost are fields every save carries whether or not a rule reads them, and the load heals all four, so a save written in either build reads back in the other. The rebuild note above applies to it for the same reason as the rest, because the draft and the rail read the flag at render time and the five flags it deals run in the browser.

`NEXT_PUBLIC_CHARTERS` is the twelfth switch and the seventh that stands outside the provisions family. It gates the charter moment at leg four: the captain's own two path charters plus one wildcard from the other eight, offered as a trio and answered with one card. The plan's rollback clause is the reason its read sits where it sits: a charter is a modifier set on the captain for the voyage, so the revert stops the offer rather than taking back what was taken. With it off no charter is offered, because the moment's own reader asks the switch first, a charter left waiting in a save written while the switch was on is simply not shown, and the report that carries a take to the room asks the switch too, so nothing is filed against a moment the build is not running. What it deliberately does not do is touch a charter already held: the card keeps its flags for the voyage, and neither the effects it writes nor the chip that draws it is read through the switch at all, which is the shape the milestone boons take for the same reason. It stands on no other layer: the pairing reads the paths the voyage dealt and the wildcard is drawn from the charters' own table, all of which exist without it. Nothing about a voyage is stored differently either way, because the charter is one field every save carries whether or not a rule reads it, and the load heals a retired or unknown card the way every other saved field heals, so a save written in either build reads back in the other. The rebuild note above applies to it for the same reason as the rest, because the offer reads the flag at render time and the rules it gates run in the browser.

All twelve switches are read the same way, and the reading is the one clause the paragraphs above do not state: each is asked as two questions in a fixed order, whether the room is a Gambit room and then what the file says. The mode is asked first, so a switch can only ever take a system away from the mode it belongs to and never hand one to the other. A Classic harbor plays the game this branch forked from whatever any of them says: the larder and its rations, the crew's names, the cold, the split hold, the pathbound cards, the escort board, the refit bench, the rumor, the draft, the module market, the milestone boons and the charters are all Ocean Gambit's, and a captain who opens a Classic harbor meets none of them whatever the file or the process environment holds. That is the boundary the branch is built around rather than a limitation of it, and it is why these twelve are not rows in the table above: they are not knobs on the game, they are the way one mode of it is taken apart.

Shutdown changed too. On `SIGINT` or `SIGTERM` the process stops accepting connections, drops the live sockets, closes the HTTP listener and disconnects the database, in that order, so work in flight is allowed to finish rather than being cut off. A second interrupt cannot start a second teardown while the first is still running.

## One rule that changed: flexible bartering is earned

Every rule the earlier build established came across untouched, with one exception, and it is worth its own heading rather than a line in a list.

Bartering now runs on two surfaces that share one board. The Captain's Exchange, on the round interface through the Parley phase, is open to every captain aboard exactly as it always was: any Renown level, nothing rationed, offers taken by whoever gets there first. Flexible bartering is the addition, and it lives in the harbor chat.

Flexible bartering opens at Renown level 10, and it is gated on both ends of the trade rather than one. Neither end is exempt: a trade is only ever as good as what the other side can put up, so a captain who has not unlocked it cannot be the partner who makes it possible. Level 10 also brings the allowance, which is one completed trade a voyage. At level 15 it becomes two.

The allowance is spent by the completed trade and never by posting, which is what lets a captain advertise the same intent on the shared board and in a private thread at once and take whichever answer arrives first. Taking an offer is never rationed on either surface, so a captain who has spent their whole allowance can still accept as many offers from other captains as they like, and a captain whose own offer was just taken is not shut out of anything. When a flexible trade does complete, every other flexible offer its own poster still had standing is retired, on the shared board and in every private thread, because those share the one allowance and the rest could only ever be accepted into a refusal. Nothing is lost to that: an offer that leaves the board returns its escrow the way a withdrawn one does. The board is swept at each phase boundary as well, so an offer nobody took during its stretch of the round hands its goods back rather than waiting for a later one.

The other half of the change is that a flexible trade can land at any point in a round, including during a phase that is already open, because the offer surfaces in the harbor chat and a captain can take it from there. A completed trade changes the hold and the purse, and every phase reads those as they are rather than as they were when the phase opened, so a shelf that was out of reach a moment ago can be affordable before the phase ends. No phase holds a cached copy of what a captain could afford, and nothing has to be restarted for the change to take effect.

## What came across unchanged

Everything the game already did. The verbatim economy from the original single player build: Hemp, Silk and Tea, the founding ports, the all or nothing pirate raid and the escort rate. The three difficulty tiers, Fair Winds, Open Waters and Monsoon Season, with their charters, pirate odds and Renown multipliers. The round, and the ready check that keeps every captain in step: [B1] renamed the leg as the six phases it always was and retired the numbered checkpoints underneath it, and what a captain does in a phase is what they did before, so the round came across with its work untouched and one less wait in it. The social economy: the barter board and its escrow, direct offers, financial aid, backing, bequest routing, ventures and Harbor Watch. The board's rules are the one thing that changed, and the section above sets out how. Harbor Pulse, Word on the Docks and Tidewatch Alerts. The Ledger Integrity Pass. Captain's Legacy, Renown and its seven titles, the nine Captain's Merits and the seven day check in. The colourblind safe palette, the fleet ticker, presence, room chat and direct messages.

Nothing in that list was retuned to make room for the new systems, with the single exception of who may barter. That is the point of the six additions: they lean on actions that were already legal rather than changing what is legal, and the barter gate is the one place that needed a rule of its own rather than a new system beside it.

## Repairs alongside the new systems

Several things that were wrong or fragile are fixed.

**Open barter offers are refunded however the phase ends.** A captain who leaves the Parley through the control bar used to walk away from their own posted offers, and the Gold held behind them went with it, because that path never told the engine what was still open. Both ways out of the phase now hand the engine the same list of live offers, so the refund lands whether a captain presses Done Bartering in the panel or moves the round along from the bar.

**The rumor price is worked out instead of remembered.** The price of a rumor was stored on the voyage and rewritten whenever the Broker's Network module was equipped or removed. It is a small sum that is right either way, but two places holding one number is a place for them to disagree, so the price is computed from the module now and the stored value is gone.

**The market remembers what things cost.** Each round records the average price paid for every good, and the Market phase draws that as a small trend line beside the shelf. A captain can now see whether Silk has been climbing all voyage before deciding whether to buy, which is the kind of read the market was always supposed to reward.

**A module draft can be abandoned.** A captain partway through choosing a shipyard module can back out and return to the picker rather than being held to the first pick they touched.

**A stranded pledge is swept.** A pledge rides on a loan: one captain backs another's borrowing, and the backer is paid when the borrower repays. A borrower who goes bankrupt keeps their socket open to watch the standings, and the voyage end sweep read that open socket as a captain who might still be about to pay. Bankruptcy is final, so the loan was never swept, the pledge riding on it never resolved, and the backer's escrowed Gold sat out the voyage. The sweep treats a bankrupt borrower as absent now, which is what they are.

**A pass over every buff, so the promise and the payout agree.** `docs/BUFF_AUDIT.md` traces every boon, every ship module, every House perk, every Age, every difficulty modifier, every Merit and every Renown rule from where it is declared to where it is read, and compares each promise to the result. The repairs it produced are all in. The two charter boons no longer share one gate, so each covers its own tier. The Silk goods list covers both goods made with Silk. The Settlement panel builds its pirate risk and its escort quote from the same functions that roll and charge them. Harbor Pulse is calibrated to the number of goods the harbor actually trades. The Purchase reference price applies the same module discounts as the counter. A failed save load no longer costs a captain their Renown level. The few numbers the interface stated that the game did not are corrected.

A worker field that was written to zero and read by nothing was removed at the same time. It changed no behaviour, and the point of removing it is that the next person reading the worker code will not spend an afternoon working out what it was for.

**A harbor master can silence a captain, and anyone can report one.** The host of a harbor has a mute button on every captain's row, and it lasts for the voyage rather than for the account: it is lifted at departure, at restart, and at the start of the next voyage, because a mute is a judgement about a table rather than about a captain. A silenced captain is told that their line did not land, and nobody else is told anything, which took a change underneath: the roster frame that carries the mute list used to go to the whole room, so every captain could see who had been silenced, and it now goes to one captain at a time, each of them seeing only what they may see. A report is the second half, available to every captain on every other captain's row rather than to the host alone, because a harbor somebody else is running still needs a remedy. It writes one row per pair per voyage, answers the captain who filed it, and tells the captain it names and the rest of the harbor nothing at all. Neither is a punishment and neither changes a rule of the game: a report is a record, and there is no review queue behind it yet.

**A captain sending frames far faster than the game can be played is slowed to a rate the game can be played at.** Nothing in the tree counted requests before, so a scripted client could emit frames as fast as its socket accepted them. Every frame now costs a token from a budget each socket holds, thirty in hand and ten a second earned back, with both numbers read off the client this build ships rather than picked: a captain trading sends at most nine frames a second, a client opening a harbor sends about nine in a moment, and the budget sits above all of it, so it cannot be reached by playing. A frame over budget is dropped rather than queued, the captain behind it is told once, and the process log gets one line. Nothing about it is recorded as telemetry, because a client sending too much is not something a voyage did.

**The voyage now runs on six named phases, and the room waits once where it used to wait twice.** The synchronized steps of a round used to be eight checkpoints, a mixture of numbers and strings that had grown one insertion at a time, and the design asks for six phases: Dawn, Market, Orders, Parley, Resolve and Dusk. Six is what the room synchronizes on now, and the two stations that were checkpoints of their own are work inside the phases that absorbed them: bartering happens in Parley, artisan management happens in Market, so a captain's turn is the turn they knew with one fewer place for the whole table to stop and wait. Which order a mode walks its six in is that mode's lap, written once on the mode record, and the two modes disagree about nothing but where the Parley sits: Classic sorts the goods before it sorts the conversation, and Gambit closes the manifest before the table opens. Every phase the engine has ever saved still reads, because a migration table maps the old values onto the new names on load, so a voyage saved before this release keeps sailing rather than landing in a phase no lap contains. The fold was safe because a phase is described in exactly one place: its label, its icon, its fill and whether it is one of the leg's six live in one table that the rail, both briefing charts and every phase panel read, where the dispatcher, the rail and each chart used to keep a table of their own. The engine's seven phase transitions no longer name the phase that follows them either. They ask the lap, which is what makes two modes able to run different legs at all, and which closed seven copies of one order.

Two faults in the ready check were found and fixed while this was in, both of them ways for a room to move when it should not. Two captains readying in the same tick could both announce the same transition, because the flag that guards it was read before a database call and set after it, so the second vote arrived at a door the first had not yet shut. A transition could also be announced naming a checkpoint that had already moved, because the frame that names the seat the room is leaving read that seat after an await. The guard is now read and set with nothing in between, and the seat being left is taken before anything in the frame goes looking for one.

**A departure pressed twice is still one departure.** The handler that sets a voyage sailing has always carried a claim, a map of the harbors whose departure is already running, so a second press is turned away while the first is doing its work. The claim was read before the handler's database reads and taken after them, which is the shape the ready check above had worn, and the price was the same: two frames arriving in one tick both found the map empty, both read a harbor that had not set sail, and both ran the whole departure. The room was told a voyage had started twice, and a loaded server saw the two alignment deals collide on the table's own key, which left one of the two sequences dead partway through its work. The claim is taken before the first await now, so the map cannot be outrun; the alignment deal reads the hand the collision left standing and sends those rows rather than failing, which is the idempotence its own comment had been promising; and the path deal looks at its map a second time with nothing awaited before it seats a deck, so two departures cannot stand two drafts over one another. The restart handler wore the same shape and takes the same fix: two restarts in one tick used to spend two epoch increments on one turn and hand the room two different voyages to name.

**A leg ends on the clock whether or not everyone has acted.** Six named phases are only an improvement if the wait in them ends, and one captain who closed a laptop used to be able to hold a harbor for the evening. Every seat of the leg now carries a budget: twenty five seconds for the boon draft, three minutes for the market and for the parley, two minutes for orders, ninety seconds for resolve, and a minute for dusk. When a budget runs out the server announces the same transition a unanimous ready set announces, on the same frame, so nothing downstream can tell which of the two ended the seat, and every captain who had not acted leaves the phase by its own defaults: the first boon on offer in the draft, and elsewhere the step their own panel would have taken, taken for them. The harbor says so out loud on its own channel as well, because a table that moved without a full ready set owes the captains still sitting at it an explanation.

The clock keeps the two properties the game already had. It runs no game rules: the engine is still pure and is still handed no clock, only the phase it is being asked to leave and the default choice, which is what keeps a voyage replayable from a save. And it does not move the room itself. The server announces, the clients transition and report, and those reports move the room exactly as they do after a vote, so there is still exactly one thing that moves a checkpoint. A room nobody is sitting in is not a room waiting on a straggler: an empty harbor's clock stops and says nothing, and a harbor abandoned mid leg still closes as an emptied voyage rather than a timed out one. The budgets are data on the phase records rather than constants in the code, so a phase that turns out too short is a number rather than a rebuild, and `PHASE_CLOCK` in the environment scales all six at once, a number between 0 and 10, where 0 and the word off are the whole feature off and every room back on manual advance. It is off unless it is asked for, and only the mode that wants a clock can ask: unset is the clock off, so a harbor that was never told otherwise ends every phase on its own ready set the way it always did, and the founding voyage keeps no clock at all whatever this is set to, which is the same boundary the twelve switches observe.

Every countdown the interface draws comes from one place. The room publishes the moment a seat runs out, and how long that seat was given, on the same frame the ready tally already rides, and both are empty on a seat with no clock, which is every seat of a harbor with the feature off. One bar reads that one pair, and it is drawn on every screen of a phase a captain has not acted on yet, including the two a captain cannot vote from: the port board, where the market's wait is not cast, and the shipyard. A captain is owed the time they have left before they decide, not only after. The wait a captain sits in names the same clock beside the tally, and the control panel names it there too. The countdown is deliberately not part of the voyage state: a moment written into that state would be a clock read inside the very thing the replay property is checked against. A leg that ends this way is recorded as one, with how many of the table had readied when the tide went out, which is the number to read when deciding whether a phase is too short.

**A captain can write down what their seat does while they are away.** The clock ends a seat somebody is sitting in; standing orders are for the seat nobody is standing at. A captain writes four instructions once, on a panel reached from the control panel in any phase of any leg, and the clock follows them when it plays that seat: which boon to take at Dawn, the dearest they will pay for each good on the market board, whether to fill the trade orders their hold already covers, and whether to buy the next hull at the shipyard. Each instruction names something a captain could have done by hand, and the clock walks into the same engine functions the buttons do, so a purse that cannot afford a lot refuses the order exactly as it refuses a click, an order the hold cannot cover is skipped rather than chased, and a boon the draft did not deal is passed over for the board's own first offer rather than taken out of the catalogue.

The record is kept with the voyage rather than with the account, so it plays the voyage it was written for, and it is read back through the same normalizer every saved field goes through: a value the vocabulary does not name is dropped, the shopping list is bounded by the goods the tree can price, and a damaged record heals to the default rather than costing a captain their voyage. That default is the switch on over an empty set, which is behaviorally the seat the clock already left, so a save written before this existed loads into the voyage it was already sailing. One switch is the whole rollback, and it is the captain's own: with it off every seat is left the way it was left before this existed, and the written set stays on the record rather than being deleted, because erasing a captain's work would punish them for trying the switch.

The lots a market's orders buy reach the harbor in a second report rather than a larger first one. A captain's own tally leaves on the frame that moved the room, read from the state as it stood when the room moved them, and the orders buy afterwards inside the same act, so the engine leaves the difference on the state and the client reports it against the same round. The server accumulates reports rather than replacing them, which is what makes a second report the right shape rather than a double count. A captain who comes back to a voyage their orders played finds the engine's own log lines indistinguishable from their own clicks, so each seat their orders worked signs the log once, after the fact, saying nobody was standing there.

**The harbor keeps a log of the voyage, and Dusk shows it to the room beside what was sent to one captain alone.** The pair is the point: the left column is what the room said out loud, written by the server and sent to every socket in the harbor, and the right column is what was addressed to this captain and to nobody else, which is the channel the alignment card already travels on. Reading them together is what tells a captain who stepped away what happened while they were gone, and what happened to them in particular. Nine kinds of fact are worth a line: the voyage leaving the dock, each seat the harbor weighs anchor for, an offer posted, filled or lapsed, a seat the tide ran out on, the audit and the maroon carried, and a captain leaving the harbor. A line is written in one place and read in one place, and the sentence lives with the kind rather than on the screen, so a line cannot read one way at one table and another way at the next.

The log is held in the process that holds the voyage, beside the checkpoint, the barter board and the session conversation, and it touches the database not at all. A server that restarts reopens its rooms with no log, and that is the truthful state of a log rather than a loss, because a line is a thing the room said while it was sailing and a room that has only just opened has said nothing yet. It is bounded at two hundred and forty lines and trimmed from the oldest end on both sides of the wire, so a long voyage cannot grow a surface without a ceiling. The line for a seat and the room's own move into that seat are written by the same block, which is why the log can neither lose a seat the room played nor invent one it did not, and the seat a voyage opens in is anchored like every other.

One defect was found in this work and fixed before the release, which is worth naming because of how it was found. A four captain walk read both columns off the drawn screens rather than off the wire, and the first line under the voyage's first leg turned out to be the second seat of the voyage, the anchor for the seat the room started in having never been written. The crowd was standing somewhere the log did not say. The anchor for the opening seat now goes through the same note every other seat goes through, and a check reads the log's first two entries back to hold it.

**A crew eats, and a captain who cannot feed it feels it in the work.** Every captain's crew eats one ration a head at each Dawn, out of a Larder that every voyage screen now carries as a number beside Funds and Reputation, so what feeding a harbor costs is a fact a captain can watch rather than a rule that arrives by surprise. Rations are bought rather than granted, priced for the crew actually aboard, from a panel on the market board that measures the hold's own room in legs of food rather than in a count, and that says plainly when there is nobody aboard to feed. A hold the crew empties reads as empty rather than as a debt, and the leg that finds it empty says so in the harbor log. From that Dawn the crew is on short rations and every producing artisan turns out half as much, floored at one item, because a task has already spent its materials by the time it resolves and a yield that rounded away to nothing would take the goods and give back silence. The shortage is not private: every captain in the harbor sees a badge on the hungry captain's row, which is the design's own requirement that a shortage be visible to the fleet rather than a private embarrassment. Small shortages are the point of the system rather than a failure of it, which is why the first reading of this layer is whether a visible hunger produces conversation rather than shame. The other half of the design's shortage, a quarter off cargo capacity, landed with the hold in the slice below: a hungry crew sails with twenty two slots of cargo rather than thirty, the quarter is read through the single capacity read the split introduced rather than applied at a second site, and it widens back the moment the larder is filled. The whole layer sits behind one flag, and the configuration section above says what turning it off takes.

**A crew that goes hungry too long loses a hand, by name, and nothing brings them back.** Two consecutive legs on short rations cost a captain the newest artisan aboard. The crew is a roster of named people now rather than a count, so the loss is a name a captain has been reading on the bench beside the others, and it holds for the rest of the voyage. The newest hand is taken rather than a random one, which is a decision worth stating: a captain can plan against a rule and cannot plan against a die, the newest is the hand they have invested least in, and a loss drawn from the engine's seeded streams would have shifted every later market card in the voyage. The name is drawn once from a pool of sixty seven and stored on the save, so a hand lost over the side is not quietly replaced by a stranger wearing their name, and a roster loaded from a save written before this build arrives with names on it rather than as damage. The voyage writes each loss down with the leg it happened on, because a captain losing hands faster than they can provision only shows when both numbers are on the record, and that record is the shape the design asked to settle now, since a boon in a later system triggers on the loss and a reveal shows it. The bench reads a name beside every artisan where it used to read a number, and the voyage summary counts the crew still aboard and names the ones lost with the leg each went over on. The rule sits behind its own flag, `NEXT_PUBLIC_CREW_LOSS`, separate from the Larder's, so the shortage and its permanence can be switched independently while a table learns the game: with it off a captain still meets named artisans and loses none, and a run of hungry legs in progress resets rather than waiting to spring when the rule returns. What the design asks to watch, the losses per captain per voyage and whether any captain spirals, has no reader on the wire in this build: the record is on the voyage, and no telemetry family carries it yet, because a family declared ahead of the events that would fill it is a schema with no rows.

**The cold takes a hand, and the clothes a captain could sell are the clothes that stop it.** Three legs in ten come up cold, and a cold leg asks for two of warmth. Warmth is not a bar a captain tops up, it is the sum of what the crew is wearing, and each garment is worth its rating times the fraction of itself that is left, so a fresh pair of Cotton Clothes is exactly two and the same pair one cold leg later is one and a half. The garments are the tree's own clothes rather than three new goods: Linen Clothes is the hemp one at one warmth and six of durability, Cotton Clothes the cloth one at two and eight, and Brocade the fine silk at three and ten, which is what makes the design's tradeoff a live decision rather than a rule, since the fine silks a captain either wears or sells are Brocade, a good with a recipe, a price and a customer. The Sachet is deliberately not in the table: a warmth rating on a perfumed pouch nobody wears would be a garment label on the wrong thing. Wearing is one way, and the panel says so before the button is pressed, because a garment taken off and put back on would be a durability bar with extra steps and the one way a captain could reset a fraction. What the crew wears is a ward against the cold rather than a sale: the ones on their backs are the ones they cannot sell. The artisan bench's wardrobe panel shows the leg's weather, the crew's warmth against what the leg asks, and every garment on the crew at the number it is worth today, and the status rail carries the same reading as a chip that wears the meaning red when the crew is short and the sea when it is dressed for it, so the forecast is readable in every phase rather than only at the bench. A cold leg met short of warmth gives the crew frostbite: the newest hand is stood down for the next leg, by name, with the mark on them where a captain can see it, and it costs them the work of one leg rather than their place aboard. Clothes wear out for doing their job: a garment loses one of its warmth a leg and two on a cold one, and one the sea has had all of comes to rags and is scrapped for four Gold rather than sitting in the hold as cargo that weighs and sells for nothing. The layer sits behind its own flag, `NEXT_PUBLIC_GARMENTS`, so the cold can be switched off while the clothes stay ordinary goods, and a voyage already carrying clothes reads back with them still on it either way. What the design asks to watch, the share of fine silks a table wears rather than sells and the frostbite count per voyage, has no reader on the wire in this build: the record is on the voyage, and no telemetry family carries it yet, for the reason the loss count above gives.

**The food in the hold is three foods now, and the hold itself is two holds.** Grain carries one meal a slot and keeps forever, salt fish two a slot and keeps six legs, and produce three a slot and turns after two, and a meal costs the same Gold whichever of the three a captain buys, so what they are actually choosing between is space and time: three times the food in a slot for a clock that runs out in two legs, a middle row that keeps six, and the full slot that never turns. The Larder is a pantry of lots rather than one number, each lot carrying the leg it was bought in, because the keeping is a fact about the oldest lot aboard rather than about the food, and the panel prints it on the row above the button. The count every rule reads and the lots the crew eats from are held to each other on every load in both directions, with grain absorbing whatever the account cannot place, so a save written by hand into an empty larder reads back as a pantry rather than as grain appearing from nowhere, and the opening twelve rations stay the one lot of grain they have always been. Beside the Larder, which is now the stores, the voyage carries a second capacity: sixty slots of stores for food and thirty of cargo for goods, so a hold full of rations can no longer crowd a captain out of the market, which is the one failure the split exists to prevent and the one the design says should therefore never occur. The shortage reaches the hold as well as the work: from the Dawn the larder is empty the cargo reads twenty two slots rather than thirty, taken off through the single capacity read that answers what fits, and it widens back the moment a captain fills the larder. Preserving is the one move that spends food to buy time, three meals of produce into two that keep six legs at the same slot of the hold, and it is offered on the market panel alone, which is the design's "at a port" kept as the panel's gate rather than as a rule in the function. The design's other clause, Quartermaster only, is one this build does not keep: the conversion ships open to every captain. The draft below is what deals a Quartermaster, so the office the clause names exists now, and the gate is a thing a later pass can add rather than one this build had to invent an office for. The three foods and their keepings ride the provisions layer, and the split rides its own switch, `NEXT_PUBLIC_SPLIT_HOLD`, so the capacity model can be rolled back while the pantry stays, which is the order the plan asks for and the reason the two are separable: the split is the riskier half. What the design asks to watch, the mix of foods actually carried, now has a record rather than a reader: every leg report of a voyage playing the split hold carries the slots that captain's ship was carrying something in and the three meal counts behind it, which is the plan's hold utilization answered and its food mix written down, while the three hundred voyage run the launch gates ask an operator to sail is J3's and has not been sailed.

**An unnamed trader sells rations at every port, and what it charges is the whole feature.** A Gambit voyage puts a Supply Barge on the quay at every leg: a vendor with no name selling food at one hundred eighty percent of what the port charges, rounded up to a whole Gold, so a port's two becomes the trader's four. No captain may take more than eight rations from it on a leg, and that ceiling is a count both captains can already read rather than a shelf they have to guess at, because the lot is drawn from the port and the leg the way the harbor's rag pile is drawn from the voyage's weather. That is what keeps the vendor in the pure engine with no state a save carries and no stock two clients could watch each other empty. What it sells is the tree's own grain rather than a fourth food invented for the occasion, so a barge ration and a market ration are the same meal in the same slot of the pantry, and what a captain buys from the trader is time.

A captain meets it as a row at the foot of the Purchase board in the Market phase, and the row names the premium before the button rather than after it: the trader's price against the port's, the rations left for this captain this leg, and, on a quay the table has already stripped, a sentence that says so and says it is a fresh lot tomorrow rather than leaving the row to read as a fault. One press takes one ration and the count falls by one. Three ceilings end a purchase, and each answers with the one it is: nothing left on the quay, a purse that cannot cover a single ration, or a hold with nowhere to put one. The vendor has no switch of its own, and the plan's rollback for this goal is the reason: reverting the Barge means reverting the mode, and the layer it stands on is the one the crew already eats from, so a table playing with the provisions layer switched off meets no barge at all.

What a voyage keeps of it is two counters, written at the one line where the Gold leaves the purse: what the voyage has spent on food and what of that went to the trader. Those two are what the balance dashboard reads, and the plan's pair of numbers sits on one screen. The front page figure is the trader's Gold as a share of all food spending in the window, taken at each captain's greatest leg rather than by adding their legs up, and the panel beneath carries that same number again with the one beside it, the share of lobbies that sailed without a single purchase from the vendor, which the plan judges above seventy percent. The share of spending has no band in the plan, so it prints as a measured number rather than as good news or bad, and a window in which nobody bought so much as a ration reads as nothing to read rather than as a zero. A voyage whose captains filed no such pair was not playing the layer and is left out of the sample rather than counted as a table that avoided the trader, and a save written before the vendor existed reads back with both counters at zero rather than as damage. The panel's other three rows still read as not measurable rather than as zeroes, and its note says plainly what they wait on: the record carries the path each captain sailed, filed once per captain when the draft settles, and no page reduces that event into a pick rate yet, so the three gates about the seat wait on a reading to write rather than on a system to build.

**Every good, every card and every charter now carries a small set of tags, and the game has a vocabulary it can say things in without naming a good.** Twelve words, closed and listed in one config module: cold, bulk, perishable, preserved, woven, luxury, armed, crewed, contraband, sealed, public and debt. Every good in the catalogue carries one or two of them, so do the three foods in the pantry, all nineteen boons, all fourteen modules, and each of the ten charters. Each one is written where the thing it describes is written, beside the id and the prose a captain reads, rather than in a table somewhere else that the next person to add a card would have to remember to edit. Nothing a captain sees changed in this release, and that is deliberate: the vocabulary ships ahead of the cards that will use it, so a voyage plays exactly as it played before, with the twelve words sitting ready.

The rule about how many tags an entry may carry is two, and it is checked rather than trusted. The check reads the content itself, all sixty five entries across the six catalogues, and refuses the build if anything breaks the line: a tag outside the list, a third tag on one entry, an entry with none, the same tag twice, a tag nothing in the game carries, a garment that is not tagged for the cold it protects against, a food that is both preserved and perishable, or a charter whose tags disagree with the raid chance and the corrupt broker its own record already describes. It runs as part of `npm run build`, before a page is compiled, which is what makes it a rule rather than a review. Three of those checks are worth calling out because they read numbers the game already kept: the wardrobe's warmth table decides which goods count as cold, the pantry's own keepings decide which foods are preserved, and a charter's raid curve decides whether it counts as armed. A tag that says something the numbers disagree with is a build failure rather than a matter of taste.

The plan's next step for this work is a scan that fails the build when a card names a good directly rather than through the vocabulary, and that scan belongs to the goal that builds the content validator, not this one. The cards that still name a good are known and listed: Silk Winds and the Silk Road Monopoly module are the two a captain will meet first, and both are rewritten against these twelve words when the card record lands. What this release adds is the language rather than the sentences: thirty one checks pin it, from the twelve words in the plan's own order through the walk over every catalogue, the two ways of asking a tag a question, the pantry and the wardrobe and the charters held to the numbers they came from, and then one check per rule, each handed a broken subject with the single thing wrong that rule exists to catch.

**Every card is one record now, and the pool a captain is dealt from is decided by the mode they are sailing.** A boon and a ship module used to be two shapes in two tables: a boon carried a modifier list, and the weights that decided how often it appeared lived in the engine as a switch statement that named all thirteen of them and read the hold and the roster by name, while a module carried nothing but its prose. Both are one ten field record now, an identifier, a kind, a power, the tags it carries, the path it leans toward, the trigger that deals it, the condition that decides how likely it is, the effect it has, the modes that offer it, and its strings in both languages, and the behaviour travels with the card: a condition is one of five, an always, a purse below a line, a purse above one, so many of a tag in the hold, or a roster that can fill the roles the card names. The engine no longer holds a single card's identifier at the draft. It asks the pool what is on offer for this captain, which is what the plan meant when it said the three cards should be drawn from a weighted pool rather than filtered out of one.

The mode field is the part with teeth. Classic offers thirty of the forty three cards and holds every one of them to a power of three; Ocean Gambit offers all forty three and runs to a ceiling of five, which is the variance answer the plan asked for, since in a competitive room one captain's good luck is another's bad evening while a shared objective can carry a wilder pool. The thirteen the base mode withholds each says which modes it belongs to on its own record rather than in a list kept somewhere else, so switching between the two pools is a change of one number on the cards that want it rather than a change to the engine. `npm run check:cards` prints both pools with their widths, and it runs as part of the build alongside the tag check.

Ten cards were renamed in the same pass, because their prose named a good rather than describing a trade. Silk Winds is Weaver's Winds now, the silk road monopoly is Woven Monopoly, Hemp Monopoly is Bulk Monopoly, and the rest read the way their tags read. A card whose own text names an item fails the build in both languages, which is the scan the previous entry said belonged here. The rewrite also carried one honest repair that the checks caught rather than a reviewer: the Smuggler's Hold icon lost its zero width joiner in the pass, so the flag drew as a bare flag with a skull beside it, and the existing check that guards that glyph refused the build before it shipped. That check exists because the same thing happened once before.

What a voyage keeps of all this is a tally of the cards it dealt and the cards that were taken, written at the one line where a card is put in front of a captain and again at the line where it is picked, so the pair the plan asks for is on the save rather than in a log. `npm run report:cards` prints the conversion per card with the appearance count beside it, against whichever database is named at the time, and a card under forty appearances prints its count and no rate rather than a percentage with nothing behind it. Two honest notes. The count is of appearances rather than of drafting sessions, so a card a captain paid to reroll into is counted again, which is what makes two cards' rates comparable. And the second language on every record is authored and not yet reachable: only English is read until a language setting exists, so the Chinese copy is data with a check behind it rather than something a captain can find.

**The five paths exist as one record, and the draft is what deals a captain theirs.** One config entry per path carries the crest a locked order card wears, the sentence that card prints, the goods the path's own ability touches, the goods whose manifest orders lock to it, the multiplier its hold carries and the Renown ceiling it banks to. It is content rather than code: the record reads no clock, no database and no environment value, so retuning a path is an edit to one file, and the id type is derived from the record itself, so a sixth path is one entry with nothing else in the tree to move. The two numbers the design leaves to the reader are read from the things they were always about. Convoy's hold is its cannon slots subtracted from the hold, because the guns that make its contract worth buying are cargo it cannot carry, and the Quartermaster's is the hold plus half again, and both land at the single place capacity is measured, so a path's modifier and a hungry crew's quarter can never fight over who answers for what fits. The ceilings come off the Renown ladder: the top rung for the Quartermaster, the rung beneath it for the four beside it.

The vocabulary changed with it, which a reader of these notes should know before they meet the words elsewhere. A captain's identity in this game is a path, built around one verb and one ability that acts on another captain, and a House is what it always was: the account level colour a captain sails under. The word Variable is retired rather than renamed. It was never printed on a screen, and that is the reason: a word a captain can spend on the thing somebody is hiding turns the first question at every table into an accusation. What the mode deals is a hidden card, and nothing a captain reads calls it anything else.

The plan's own evaluation for this work was a throwaway sixth path added to the record to prove that no other module had to be edited, and it was run for this build rather than described. The whole tree typechecked and built with the sixth path standing, and the full suite passed against it. The first run failed exactly one check, and the check was wrong rather than the path: it had pinned a single good as belonging to nobody, which was true of the five paths and not of the module, so a sixth path claiming it read as a regression. It now holds the property the design actually needs, that the catalogue still carries goods no path claims, which is what keeps the board's ordinary orders ordinary.

**The trade board posts three orders no captain can fill yet, and each says why on its own face.** Six orders are what a charter schedules and three are the paths' own, appended after the draw rather than mixed into it, so the six a table is dealt with the feature switched off are the six it was dealt before the feature existed, card for card and reward for reward. A pathbound card draws greyed and dashed, stamped with the crest and the name of the path that would open it, and in place of the trade button it prints the sentence that path's record carries, because the lock is read from the good the card demands rather than written onto the card, and a retuned pool moves the labels with it. A captain meets a card they cannot fill whenever it waits on a path other than the one they drew, which is the design's teaching rather than a staging state: a deck deals one path to a captain and the board draws from every path's pool, so the locked card is met on the very first leg rather than held back for a later one.

The three are drawn from the two pools the manifest can trade. The Quartermaster's pool is the provisions, bought at a meal price and never sold back to a port, so a board order for them would price like any other order against a ration that costs two Gold, which would turn the till into a levy on a captain's own larder; that seat brings the board no order of its own, and the three slots come from the loom and the aroma pools. One guard answers whether a card is a captain's to fill, and the board, a captain's own press, the standing orders and the suggester all ask it, so a standing order cannot fill what its own captain could not press. The switch is read at both ends, at the draw and at the lock, so a board dealt while the feature was on plays as six ordinary orders once it is off rather than leaving three cards grey forever, and nothing about a voyage is stored differently either way. The leg report's dealt count reads past the locked cards, so nobody is charged three expired orders a leg for a feature none of them can touch. What the plan asks to watch, whether locked cards are looked at at all, has no reader on the wire in this build: what the spine carries about a board is the leg report, and orders dealt and filled cannot tell a card that was looked at from a card that was not, so that reading waits on the hover state the plan's own iteration clause names.

**A Convoy captain can sell a leg of protection, and the sea decides whether it was a good trade.** The escort contract is the first market in this game where both sides are guessing about the same hazard: a seller names a fee, a buyer takes it, and for the length of that leg the buyer's raids become the seller's problem. The fee moves when the two captains agree rather than when a raid lands, so the seller is paid for the leg whatever the sea does, and the claim moves only when a raid actually comes, which is the order the design publishes: contracts pay first and escorts absorb raids. What the guns beat off is one number, read by the claim and by the odds both panels quote, so a captain reading their chances and the engine settling a claim are never reading two figures that merely agree. A seller who leaves the harbor takes their contracts with them, both the offers nobody had taken and the agreements already struck, because cover is read off the room's board and a board still carrying a departed seller would leave the buyer protected by guns that are no longer in the harbor. That is the plainest of the gaps the design leaves for betrayal, and the rules do not close it, because a contract is a promise about a leg rather than a guarantee about a captain.

The board belongs to the room rather than to a captain, and it is held beside the barter board for the same reason: an agreement between two captains is an object no single client can be the authority over. It is also the one board here that is sent per socket rather than broadcast whole, because a direct offer belongs to two captains and a claimed contract's raid figure belongs to its seller, so two captains in one room can legitimately see two different boards. Two things the server deliberately does not do are worth naming, and both are the barter board's line rather than a new one. It does not know who holds the Convoy path and does not ask, because a path lives in a captain's own save and the server has never read one. And it prices no claim and clamps none either, since what a raid would have taken is the covered captain's own report and what the guns ate is worked out on the seller's client against the seller's own purse. What it does enforce is the claim's ordering: one claim per contract, only against a contract that was agreed, only from the captain whose name is on it, and only in the leg it was sold for. Nothing here is durable, which is the design's own instruction rather than a shortcut, so a save carries no contract at all, only the tally of what already settled and the ledger of movements already applied. The switch is `NEXT_PUBLIC_ESCORT_CONTRACTS`, and the configuration section above says what turning it off takes. What the design asks to watch, contracts sold per leg per Convoy captain and the ratio of fees collected to losses absorbed, has no reader on the wire in this build, and the reason is not a missing record but an empty market: a Convoy captain only exists once a fleet deals its paths, which the draft below now does, so the panel has its seller from the first voyage sailed under this build and what the reading waits on is tables with strangers at them rather than anything absent from the tree.

**A mode documents itself now, and a captain who picks the new one is taught the game they are about to play.** The surfaces that teach the rules were written for the founding voyage and never told the other one. The tutorial drew Classic's lap by hand and promised, on its second page, that failing the bills ends the voyage, which is the one thing Ocean Gambit is built not to do: a captain who picked that mode read that their seat was gone, and the whole design rests on the opposite, that a captain whose books fail keeps their card, their vote and their say at the table. The guide's phase list was a fourth drawing of the same lap, and the lobby's manual ended its settlement page on the same false sentence, so a captain could be told the wrong rule on three screens before the first Dawn. The second complaint was the quieter one and the same defect: a captain who read all three came away knowing how the founding voyage plays and nothing about how theirs does.

The mode record now owns both halves of the answer. `failureRule` is one sentence for what happens to a seat whose books fail, and `differences` is the list of what a mode changes, empty for Classic because the founding voyage is what the others differ from. Every surface reads those fields rather than holding a copy: the tutorial gained a page for the mode and its round page renders the record's own briefing rather than a hand drawn chart, so the lap a Gambit captain is shown is the lap the record carries and the mode that moves the manifest ahead of the table is the one that says so. The guide prints the mode's line, its rule and its list. The manual prints the same list on a page of its own, second, right after the harbor, because a captain asks what this voyage is before they ask how a phase works, and the settlement page no longer answers that question with the founding rule. The advice keeps a heading per mode and states the rule where the rule does not end a career. The Welcome screen, which is the first thing a crew reads, names the mode, its stake and where the full list is, and the number of rounds it greets the crew with is the number the voyage was pinned to.

The words around it were corrected too. A voyage is the whole run and a round is one lap of it, and the Welcome screen greeted every crew with "8 Voyages await" above an eight round voyage, so the first screen of the game had the two words the wrong way round. What is different can be read in the room as well as in the lobby, because all four surfaces print the one array rather than four answers to the same question, and the smoke suite holds them there: it reads each surface for both modes at every tier, checks that the record's own sentences arrive intact, that Gambit is described differently from Classic everywhere, and that no word any of them prints carries a dash.

**The pirate flag is one glyph again.** The icon beside the pirate stage on the settlement panel is a flag joined to a skull by a zero width joiner, a character that is invisible in the source and means nothing to the compiler, and a documentation pass over that panel dropped it. The stage then drew a bare black flag with a skull floating beside it, which is a thing only a player could see and only a player did see. The joiner is restored, and the suite now builds both the joined and the unjoined sequences from code points rather than spelling either one, checks that the joined form is the one the panel draws, and refuses either unjoined form anywhere in the tree. The check distinguishes the two flags a captain meets: the lone black flag on the bankruptcy line is a flag rather than a pirate, and it stays.

**A Loom captain can put a garment right for another captain, and the price is the whole argument.** Clothes lose a point of wear every leg and two on a cold one, so a wardrobe is a clock, and the harbor tailors will always sell one point of it back for five Gold, once a leg. The refit bench is the other half of that sentence: a Loom captain puts three points back in a single leg, on any garment they name, for whatever fee the two of you agree to. That gap is the trade, and it is why the bench stands on the Market phase's port board rather than in a panel of its own, beside the pile the path draws its supply from.

A refit is offered by the seller and agreed by the customer, the same mutual acceptance the escort contract uses, because a refit is the first thing in this game that touches another captain's state and it needs a clear rule about who authorizes it. One pair of hands takes on one refit a leg, an offer can be addressed to a single captain so nobody else can take it first, and an offer nobody takes before the Market closes is gone, while a refit that was agreed stands for the leg it was agreed for. The fee moves when the two captains agree rather than at the end of the leg, and the points go back on the customer's own garment on the customer's own machine, so the number a row quotes and the number their warmth moves by are one number rather than two that agree. What the server enforces is the ordering rather than the price, because the server has never read a captain's hold or their wardrobe: it checks that a fee is a whole number of Gold inside the published bounds, that the offer belongs to this leg and this phase, that the captain named is in the harbor, and that a seller has not already taken work on this leg, and it says which of those failed rather than dropping the frame.

The path's supply is the fleet's own scrap, and the fleet's scrap is the weather. A pile of rags comes ashore after a cold leg, one to three of them, drawn on each captain's own machine from the voyage's own numbers, so two Loom captains at one table each take their own share of the same pile rather than racing for a shelf neither can see the other emptying. A rag costs four Gold and takes a slot of the hold like any other cargo, and two of them go back on the loom as one Linen Clothes, which is the crafting chain this path also holds. The switch is `NEXT_PUBLIC_REFITS`, and it stands on the wardrobe layer rather than beside it, so a voyage with no clothes has nothing to put right and the bench stays shut. What the design asks to watch, whether a Loom captain is the poorest at the table on warm legs and among the richest on cold ones, needs tables with strangers at them rather than a suite, and it is named here rather than quietly claimed: if the income is flat across leg types, the weather is not reaching the path.

**An Aroma captain can move a price at the next port, and the whole harbor will know they spoke.** Once every three legs, at the Parley, a captain who holds the Aroma names one commodity and leans it: the next port prices that good by up to ten percent, more or less, which is the same hand the Harbormaster already leans a port with. What the table is told is who spoke and which good they named. What it is not told is which way they leaned, and that is the feature rather than a detail of it, because the direction stays with the speaker only until the market they moved has been priced. One leg later the direction is public, and the row reads as a price that moved because somebody said so at the table. A captain who holds none of the paths reads the same board everyone else does and can act on it, because a price move nobody can attribute to a name is not the mechanic the design is paying for.

The design calls this the best idea in the base game and the argument is worth restating, because it is the reason the feature ships to every table rather than only under the new mode. It is a lie an ordinary honest captain can tell, so a suspicious price movement stops being automatic evidence of a traitor, and a table that has learned to read it has learned that public information can be weaponized. What a captain actually buys with a rumor is the market of one leg, since they can trade against their own call before the port prices it, and the cooldown is measured in legs from their last publication rather than wound down on a counter, so the wait a captain reads on the desk and the wait the server enforces are one number. Two captains naming the same good are one voice the harbor has heard twice and two captains pulling against each other cancel rather than averaging into a move nobody called, so the loudest the bazaar can get is the loudest a single call can get. The goods a captain may name are the goods the coming market actually trades, read one leg ahead, which is what lets a captain speak about a cargo in the leg before the harbor stocks it, and the price band the market is drawn from does not move with it: a rumor moves a price, never a board, and the same seed deals the same cards whether or not anybody spoke.

Nothing about a rumor is durable, so a captain who reloads is handed the board the room holds rather than a copy of their own, and a captain who leaves the harbor takes their name off the roster and leaves their rumor standing, because a rumor is not a promise to anybody and the market it moved has already priced it for everyone still sailing. The desk is drawn at the Parley table under the protection market, and the switch is `NEXT_PUBLIC_BAZAAR`, which the configuration section above describes. What the design asks to watch is false positives, how often a price move is cited as evidence against a captain in the hidden role mode and whether honest rumors account for a real share of those moments, and that reading needs tables with strangers at them rather than a suite.

**A locked order is reachable once a voyage, and the reach costs forty percent of the payout.** A table meets cards it cannot fill whenever a card waits on a path no captain at it drew, and those cards are a promise the game now keeps at a price rather than a wall. A Free Captain may take one of them, any one of them, without joining the path it waits on: the card offers the borrow on its own face, the fill goes through the same engine call every other fill goes through, and what it costs is two fifths of the order's face value, taken at the one line in `completeOrder` that names a reward, so the freight, the tax and the purse all settle against a single number afterwards rather than three that were each adjusted. The card says the price before it is paid: a locked card held by a Free Captain quotes the reduced payout as its own Reward figure and the net below it as that payout less its freight and its VAT, so the number a captain reads and the number their purse moves by are one number rather than two that agree, and the allowance is printed on the same card, before the press and after it, as a count of what is left.

The allowance is spent by the fill and reset by the voyage, and it lives on the save as a count of what has been taken rather than what is left, so the field only ever climbs inside a voyage and one reader is the only place the limit is applied. Nothing here is on the server, and that is the line every client authoritative fill in this game draws: the server does not know a borrow happened, does not price one and clamps none, because the purse it would be judged against is the captain's own save. The switch is `NEXT_PUBLIC_PATH_ORDERS` rather than a new one, because a borrow is a way through a lock and a build with no locks has nothing to borrow past: with it off no card is dealt locked, the guard answers false on its first line, and no card draws a borrow or a price it would have changed. Nothing durable is added at all, which is what makes the design's own rollback note true rather than hopeful: one integer on a save that is the captain's own, one line in a ledger that already existed, and no schema, no row, no endpoint and no dependency. What the design asks to watch, the usage rate and whether a borrow lands on the order that would have been the best fit for a real path, needs tables with strangers at them, and the path pick rate band it also names waits on the draft, because a path is content until a captain can be dealt one. The suite pins the mechanism those readings would read in sixteen checks, and the drawn card is read in a real browser in twenty three more, which is where the payout, its net and the purse's movement are held to each other on screen.

**Every captain is dealt a path now, and the one they sail under is a choice they make at the dock rather than a role they were given.** The deal is three cards face down, keep one, pass two to the left, keep one of the two that arrive, then sail on one of that pair, so the three beats take a table of two the time it takes to press three buttons and can never take longer than forty five seconds, which is the ceiling the three step clocks add up to rather than a pace every table waits out. The hands are the server's: a captain is sent their own cards and a count of the captains still choosing, and never anybody else's, which is why the deck is shuffled and dealt by the room rather than drawn by the browser. The plan's own constraint holds by construction rather than by luck, because each path's share of the deck is a weight in one table and the deck is sized for the table, so the Quartermaster card is in every deck at every size this lap can seat, and a reader who wants to retune how often the fleet meets a path edits that one table. The half of the feature that costs something is the switch: once a voyage, at a port, in legs three through nine, a captain sets their papers aside for another path, paying a fee that climbs with Renown to a ceiling of one hundred and fifty Gold, forfeiting the pathbound orders their old papers opened and had not filled, and the whole fleet sees it, because the publication is as much the price as the fee is. The room publishes the change and the captain's own client applies it off that frame rather than off the press, so a switch the harbor refused is a switch that cost nobody anything, and each change is filed in the voyage log with the leg it happened on, so a reader can tell a table that switched from one that never did. The rail carries the path as an identity chip from the moment the deal settles, and the three locked cards the trade board has been posting all along now say which path would open them, which is the first time a captain can hold the card that waits for it.

**A module bolted to a hull can leave it now, and what it costs is whatever two captains at the Parley agree.** The shipyard ladder has bolted modules on since the first voyage, and what it never had is a way off: a module drafted at the yard stayed on the hull until another draft displaced it. The module market is the way off, and it is the third consent board this epic built, one captain lists a module they have aboard, another takes it at a price the two of them agree, and the module changes hands at the Parley table. It exists for the same reason the two boards before it do, because the build layer deserves liquidity and the table deserves a class of deal that is not about commodities: there is no reference price on either side of it, which is what makes it a negotiation rather than a shelf. Any captain may sell, and that is this kind's departure from the escort and the bench rather than an omission: cover and mending are path abilities, but a module is a thing bolted to a hull, so a captain's only qualification is owning one. The plan's own named rule is the settle: a module traded while equipped is taken off by an automatic unequip rather than blocked, and the seller's own machine is what takes it off and unwinds exactly the accounting the module carried for as long as it was installed, so a module sold mid voyage gives back the hold or the discount it was applying in the same breath that it leaves.

The server keeps the ordering rather than the hulls, because the server has never read a captain's save. It checks that the thing listed is a module the yard can bolt on, so a row no buyer could take never reaches a board; that the fee is a whole number of Gold inside the published bounds, refusing rather than clamping and naming both ends; that the offer belongs to this leg and to the Parley, since a module changes hands at the table rather than mid leg; that one module carries one row for the whole leg through every status rather than the open ones alone, because a settled sale is the strongest of the reasons a module is not for sale again this leg; and that an offer aimed at a captain aims inside the harbor. What it deliberately does not do is bound either side to one agreement a leg, and that is the other departure: the escort bounds its buyer because one captain's cover is one field and the bench bounds its seller because one Loom has two hands, but a hull's modules are a shelf rather than a field, so what bounds a sale is the per module rule above and what bounds a purchase is the buyer's own slot count, read on the buyer's own panel rather than counted by the room. Two corners are worth naming because a reader will look for the missing check and should find these instead. The buyer pays the agreed price out of what their purse actually holds and the seller credits the agreed price, because the price rather than the payment is what the two captains shook hands on. And an agreed trade always completes, even onto a hull whose slots are full: the two machines cannot see each other's hulls, and a module lost between two clients would be a durable thing destroyed by a race, so the buyer bolts it on and every slot reader in the tree floors at zero and answers full, which is a captain who swaps at the yard before drafting again rather than a subsystem that disagrees with itself.

What a voyage keeps of it is a tally and a ledger. Four counters sit on the save, one side each way for the captain's own dealings, what left their hull and what it earned and what joined their hull and what it cost, and the leg report carries the seller's two, because the plan's own number is trade volume between captains and a volume is a number about sales. The ledger is a count per module card, written at the one line where a sale settles, and it is what turns the plan's second reading, which modules are equipped against which are traded away, into a report rather than a guess: the equipped half is already in every save as the hull itself, and `npm run report:modules` puts the two columns side by side against whichever database is named at the time, walking the module list from the pool rather than typing it out, so a module added tomorrow appears the moment it exists. Both the tally and the ledger heal at the load site the way every field in this tree does: a save written before the feature reads as a captain who has moved no module, and one carrying rubbish where a count should be reads as a captain who moved none rather than one whose next trade throws. The ledger is also the idempotence: a reload between an agreement and the frame that carries it must not move the same Gold twice, and a board that reports the same row again moves nothing again. The harbor's log gets the market's two lines, a listing and a sale, each read through the card pool so the line and the chip on the hull say the same words about the same module. The switch is `NEXT_PUBLIC_MODULE_TRADES`, and the configuration section above says what turning it off takes. What the design asks to watch beyond the volume is the reading across the two columns, and that waits on tables with strangers at them rather than on anything absent from the tree: the record and the report are both here, and what a reader would want from them is a module that is always equipped, which is the row that would say a card is a tax rather than a choice.

**Every boon a captain is dealt is public to the whole fleet now, the cards they were shown and the one they kept.** A draft happens at the Dawn and, for the milestone moments, wherever a moment lands, and until this build the table saw only the effects. The record is written by the pick itself rather than by a report of it: the engine stamps the trio and the kept card onto the save at the one line where a card is taken, built from what the screen dealt rather than from a fresh draw, and it changes for four ordinary reasons, a click, a standing order, a dawn run out by the clock, and a moment's answer. What a captain presses at the draft is a held choice rather than a published one, and that is deliberate: the record is written when the room runs the pick at the advance, so the waiting screen's way back leaves no row and no frame, and what reaches the fleet is what was kept rather than what was nearly kept. The board itself is one panel drawn at the draft and at the Parley table where the plan puts the argument, one row per captain named by the roster, the reader's own row marked as theirs, one chip per card of the trio with the kept card marked by weight and fill rather than by colour alone, and a board with no records draws nothing at all rather than a placeholder, because the plan's record is a record.

The server keeps the ledger rather than a log: one record per captain per harbor, replaced by the next pick, with the whole table's map broadcast to the room after every accepted report rather than one entry patched in, because the map is what the panels draw and a client patching into a map it may never have received would be a second copy of the same arithmetic. A report from an older leg than the record the captain already holds is refused rather than stored, so a stale tab cannot rewind the table's picture of a captain who has since picked, and a joiner is handed the ledger the moment they join, because public state a reload can miss is state the table has to say again. ## What is still to come

Two of the eighteen Manifest systems are not in the game.

**House Rally** (Manifest 09) was designed and not built. It would have given a harbor where most of the captains share a pledge a flavour banner and a bonus House standing at voyage end. It is the last system on the roadmap.

**Bilingual Harbor** (Manifest 15) was built in full and then removed at the owner's request. It does not come back without a fresh owner decision.

## Where the two repositories differ outside the game

The game is a strict superset. The tooling around it is not, and it is worth knowing which repository carries what.

Two commands stand beside the suite. `npm run check:private` scans the tree for a second path to any secret the game hides, eight rules at a time, and fails on the first one. `npm run check:closed-test` is step zero of the closed test: it refuses to bless anything but a local SQLite file whose name begins with `closed-test`, prints that name beside the counts of what is already inside, and never prints any part of the database URL. The deployment surface moved from prose to a file. `railway.json` in the project root is the whole host configuration, so a service builds and runs from the repository as it stands rather than from a guide somebody follows by hand. It carries one deliberate difference from a conventional Node deployment, and the README says why: the hosted service runs the development server, because `next build` wants more memory than the smaller plans provide and a build killed halfway is a deploy that never lands. The same work added `/api/health`, the readiness probe the host repeats before and after it promotes a deploy, which answers from the process and reads nothing else so a busy database cannot fail it.

2.2 is also on Prisma 6 rather than Prisma 7, which is why the connection string lives in `prisma/schema.prisma` here and the client needs no driver adapter, and why there is no `prisma/migrations` history in this repository. `db:push` is the way the tables get created.
